# M04 — API + SSE + UI v1

**Goal:** the ticket agent from M03 runs behind a FastAPI server and a browser UI. You pick a persona, chat over several turns, watch the answer stream token by token, and see every tool call appear live in an event timeline. The UI shows exactly the same events that the JSONL log and (from M07) the evaluator see.

**Estimated effort:** 2 sessions. Session 1: design decisions, streaming adapter, per-request event delivery, thread ownership, SSE endpoint. Session 2: UI, multi-turn, cancellation, demo, verification.

**How you learn in this milestone:** Claude Code writes all code. You (1) answer the Design decisions in §3, (2) predict the demo output, (3) run it and use the UI, (4) do the Break-it exercises, (5) go through the Review checklist, (6) explain one scenario back.

**Learning objectives:**
- How LangGraph's v3 event stream is shaped (`messages`, `tools`, `values`; namespaces; `seq`) and why it is translated into **our** event contract at one boundary instead of being exposed directly (W1 L3, W2 L3).
- How a streaming harness handles the hard parts: redaction, an allowlist toward the browser, client disconnects, and bounded queues (W1 L3).
- What a **thread** is (checkpointer + `thread_id`), and why a thread must be bound to its owner (W2 L3).

**Course topics:** W1 L3 (streaming events, SSE mapping, redaction, cancellation, backpressure, checkpointer + `thread_id`), W2 L3 (v3 raw events with `seq`/namespaces, public envelope with version and allowlist).

Already verified on 2026-11-23 (langgraph 1.2.24, langchain 1.5.2, Python 3.13):
- `await agent.astream_events(input, config, context=..., version="v3")` returns an **`AsyncGraphRunStream`**: the call itself must be awaited, then iterated. It also exposes projections (`.messages`, `.tool_calls`, `.values`, `.output`, `.interrupts`, `.subgraphs`, `.lifecycle`, `.abort()`).
- Iterating it yields raw events `{"type": "event", "method": ..., "params": {"namespace": [...], "timestamp": ..., "data": ...}, "seq": n}`. For a `create_agent` run the methods are `values`, `messages` and `tools`:
  - `messages`: `data` is `(protocol_event, metadata)`. Protocol events: `message-start`, `content-block-start`, `content-block-delta` (`{"type": "text-delta", "text": ...}` or `{"type": "tool-call-delta", ...}`), `content-block-finish`, `message-finish`. `metadata["langgraph_node"]` names the node (`"model"`).
  - `tools`: `{"event": "tool-started" | "tool-finished", "tool_call_id", "tool_name", "input" | "output"}`.
- LangGraph prints **`LangChainBetaWarning: The v3 streaming protocol on Pregel is experimental`** (see decision D1).
- **`ScriptedChatModel` breaks under streaming.** A scripted `AIMessage` with only `tool_calls` makes the agent fail with `RuntimeError: v2 stream finished without producing a message`. The fake must implement `_stream` / `_astream`: one chunk carrying `tool_call_chunks` for a tool-call message, word-by-word text chunks for a text message. (Prototype verified: with that change the v3 stream shows `tool-call-delta` and `text-delta` events exactly like a real model.)
- `ToolRuntime` exposes `tool_call_id`.

## 3. Design decisions (🎯 you, before any code)

Record your choice and one sentence of reasoning under *Notes → Decisions*.

| # | Question | Options and consequences | Recommended |
|---|---|---|---|
| D1 | Which LangGraph stream do we consume? | **A** `version="v3"`: what the course teaches; structured protocol events, `seq`, namespaces; marked *experimental*, may change. · **B** `version="v2"`: stable, older shape, less structure. | **A**, isolated in **one** adapter module and with `langgraph` pinned to the current minor, so a v3 change touches one file. Silence the beta warning only inside that module. |
| D2 | Where does the SSE stream come from? | **A** From our event bus: a per-request `QueueSink` receives the same Event v1 objects as JSONL and memory; SSE serialises them → one contract for UI, logs and evals. · **B** Translate LangGraph events directly into SSE → faster to write, but the UI sees a second, different contract. | **A** |
| D3 | LangGraph's own `tools` events vs the wrapper's `tool_started`/`tool_finished` | **A** Use only the wrapper's events (they carry status, reason code, duration, redaction); ignore v3 `tools` events in the adapter. · **B** Forward both → duplicates in the timeline, and the v3 ones are unredacted. | **A** |
| D4 | Are `token` events written to the JSONL log? | **A** No: tokens go to the browser only; the JSONL sink excludes `token` (the log records *what happened*, not the full text of answers). · **B** Yes → full transcripts on disk, a privacy and size question. | **A** |
| D5 | Who creates `thread_id`, and who may use it? | **A** The server creates it (`POST /api/threads`) and binds it to `(tenant_id, user_id)`; every chat call checks ownership; an unknown or foreign thread → `404` (same answer for both, nothing leaks). · **B** The client invents ids → anyone who learns a thread id can read that conversation from the checkpointer. | **A** |
| D6 | The browser disconnects mid-answer. | **A** Cancel the agent run and record `run_finished(cancelled)` → no wasted model calls. Requires widening `run_finished.status` with `"cancelled"`: allowed in v1 if consumers treat unknown statuses as "other" (record that rule next to the versioning rule) and the snapshot is regenerated. · **B** Let the run finish in the background → simpler, but you keep paying for an answer nobody reads. · **C** Record it as `failed` → no schema change, but cancellations pollute failure metrics (M07, M16). | **A** |
| D7 | Which events reach the browser? | **A** Explicit allowlist per kind and field, default deny: a kind added later is invisible to the UI until someone adds it on purpose. · **B** Send every event (they are already redacted) → simpler, but any future payload field is exposed automatically. | **A** |

## 6. Streaming adapter: `stream_turn` (🎯 decide & verify)

```python
async def stream_turn(
    agent: HarnessAgent, *, ctx: RequestContext, message: str,
    repos: Repositories, bus: EventBus, clock: Clock, entrypoint: str,
) -> TurnResult: ...
```

The streaming sibling of `run_turn` (M03). It:
1. Emits `run_started`.
2. Calls `await agent.astream_events(..., config={"configurable": {"thread_id": ctx.thread_id}}, context=ToolContext(...), version="v3")` and iterates it.
3. For each raw event:
   - `messages` + `content-block-delta` of type `text-delta` → `token` event (`text`, `agent`).
   - `messages` with tool-call deltas → ignored (the wrapper records the tool call, D3).
   - `tools` → ignored (D3).
   - `values` → ignored in M04 (it is the full state; M05 may use it).
4. Collects the final answer text.
5. Emits `run_finished` in a `finally`: `completed`, `failed` (then re-raise, like `run_turn`), or `cancelled` when the task is cancelled (D6; re-raise `CancelledError` after recording).

Rules:
- This is the **only** module that knows the v3 protocol (D1). If LangGraph changes v3, only this file changes.
- `run_turn` and `stream_turn` must produce the same non-token events for the same scripted run (test it).

| # | Case | Expected |
|---|---|---|
| S1 | Scripted run: tool call, then "Ticket T-0002 is in progress" | Events in order: `run_started`, `tool_started`, `tool_finished`, several `token`, `run_finished(completed)`; tokens concatenate to the answer |
| S2 | Same run through `run_turn` | Same sequence without `token` events |
| S3 | Second turn on the same thread | The model receives the first turn in its message history |
| S4 | Second turn on a **new** thread | No history |
| S5 | Task cancelled after the first token | `run_finished(cancelled)` recorded; no further model call |
| S6 | Tool bug (D1 from M03) | `tool_started` without `tool_finished`, `run_finished(failed)`, exception re-raised |

## 7. SSE allowlist and framing (🎯 decide & verify)

```python
ALLOWED: Mapping[EventKind, frozenset[str]]   # kind → payload fields the browser may see
def to_sse(event: Event) -> ServerSentEvent | None: ...   # None = not sent
```

Initial allowlist (D7):

| Kind | Payload fields sent |
|---|---|
| `run_started` | `entrypoint` |
| `token` | `text`, `agent` |
| `tool_started` | `tool`, `call_id`, `args` |
| `tool_finished` | `tool`, `call_id`, `status`, `error_code`, `duration_ms`, `summary` |
| `run_finished` | `status`, `duration_ms` |

Every SSE frame carries the envelope fields `schema_version`, `seq`, `ts`, `request_id`, `namespace`, `kind`; never `thread_id` internals beyond what the browser already knows, never `workload`.

| # | Case | Expected |
|---|---|---|
| E1 | `tool_started` | Only the listed fields; args already redacted by the recorder |
| E2 | An event kind not in the allowlist (e.g. a future `usage_recorded`) | Not sent |
| E3 | A payload field not in the allowlist | Dropped |
| E4 | SSE `id:` field | Equals `seq` |

## 8. HTTP API

| Method & path | Auth | Body → response | Owner |
|---|---|---|---|
| `GET /api/personas` | none (demo) | → seed employees: id, name, department, roles | ⚙️ |
| `POST /api/session` | none (demo) | `{employee_id}` → `{token, expires_at}` | 📖 |
| `POST /api/threads` | Bearer | → `{thread_id}` | ⚙️ (uses `ThreadRegistry`) |
| `POST /api/chat` | Bearer | `{thread_id, message}` → `text/event-stream` | 🎯 decide & verify |

`POST /api/chat`:
1. Token → `Principal` (invalid / expired → `401`).
2. `ThreadRegistry.require_owner` (→ `404`, D5).
3. Build `RequestContext`, a per-request `EventBus([jsonl, memory, queue])`.
4. Start `stream_turn` as a task; stream `to_sse(event)` from the queue until the queue closes.
5. On client disconnect: cancel the task (D6); the `finally` in `stream_turn` records `run_finished(cancelled)`.

| # | Case | Expected |
|---|---|---|
| H1 | No / bad token | `401`, no run started |
| H2 | Valid token, foreign thread | `404`, no run started |
| H3 | Valid request | `200`, `text/event-stream`, frames in `seq` order, last frame `run_finished` |
| H4 | Client disconnects after the first token | JSONL shows `run_finished(cancelled)` |
| H5 | Message empty or longer than 4,000 characters | `422`, no run started |

## Notes (fill in)
### Version check
Checked 2026-11-23 against PyPI; installed = latest for every package:
- `langgraph` 1.2.24, `langchain` 1.5.2 (core 1.8.4): v3 is **still experimental**. `_pregel_stream_v3` is decorated `@beta("The v3 streaming protocol on Pregel is experimental.")`. `create_agent(..., checkpointer=...)` exists.
- `fastapi` 0.165.0 (starlette 1.10.0), `uvicorn` 0.54.0, `pyjwt` 2.15.1, `httpx` 0.28.1 (dev).
- **Differences from the milestone text:**
  - **`sse-starlette` not added.** FastAPI 0.165 ships native SSE (`fastapi.sse.EventSourceResponse` + `ServerSentEvent`, used as `response_class=` on a path operation that `yield`s). It works with `POST`, inserts keep-alive pings by itself, and the generator is cancelled through Starlette's disconnect handling. Re-add `sse-starlette` only if H4 (disconnect test) shows the native version is not enough. Note: FastAPI's `ServerSentEvent.data` is always JSON-encoded; use `raw_data` for pre-serialised JSON.
  - **Streaming fake: a tool call takes 3 chunks, not 1.** With a single chunk the v3 stream emits `content-block-start` + `content-block-finish` and **no** `tool-call-delta`. `ScriptedChatModel` now streams name + id, then the arguments, then an empty closing chunk, like a real provider. The `chunk_position="last"` marker must not sit on the arguments chunk, or LangChain parses that chunk alone and drops the arguments (`tool-error`).
  - A text reply streams one chunk per word, whitespace kept (`"Ticket "`, `"T-0002 "`, ...); the v3 stream shows one `text-delta` per chunk.
- PyJWT: `jwt.encode`/`decode` are partially untyped (optional `cryptography` key types), so two `pyright: ignore` comments sit in `api/auth.py`.
- An agent built **with** a checkpointer requires `configurable.thread_id` on every call. `run_turn` does not pass it yet; that is part of the step 2 orchestration work (S2: `run_turn` vs `stream_turn`).
### Implementation notes (step 2)
- **v3 has no background task** (`AsyncGraphRunStream`: "caller-driven pumping"). The graph only advances while `stream_turn` pulls the next event, so cancelling the task cancels the in-flight step, and `async with` calls `abort()` on any early exit. D6 therefore really stops model calls; it does not just stop listening.
- **Beta warning (D1):** silenced with `langchain_core._api.suppress_langchain_beta_warning()` around the `astream_events` call only. It is a context variable (this task only), not a process-wide `warnings` filter, so it is safe with concurrent turns and does not hide other warnings.
- **`QueueSink.abandon()`** (added): on disconnect the route abandons the queue *before* cancelling the run. Without it, a full queue with no reader would block `run_finished(cancelled)` in the run's `finally`. `close()` never blocks either.
- **A run that finishes before the disconnect is noticed is `completed`**, correctly. With the scripted model the whole answer fitted in the queue before the hang-up was processed (first H4 attempt). The fake now yields to the event loop after each chunk, like a real provider waiting on the network, and has `chunk_delay` to simulate a slow model (H4 and demo scenario 5 use 20 ms).
- **Errors before the stream:** a streaming response is already `200` once it starts, so token, ownership and body checks run in a dependency (`prepare_turn`) *before* the generator; `401`/`404`/`422` are plain HTTP errors and no run starts.
- **`httpx.ASGITransport` buffers the whole response**, so it cannot hang up mid-stream. `demos/asgi_client.py` speaks ASGI directly (like uvicorn, spec 2.3) and sends `http.disconnect` on demand; H4 and demo scenario 5 use it.
- **Run tasks are kept in `AppState.running`**: asyncio holds only weak references to tasks, so a disconnected run could otherwise be garbage-collected before its `finally` ran. Lifespan shutdown cancels runs still in flight.
- `JsonlSink` drops `token`, so `seq` in the JSONL file has gaps where tokens were (e.g. `seq0 run_started · seq2 run_finished`). That is expected: `seq` orders the request's events, not the file's lines.
### Decisions
- D1: **A** (`version="v3"`). It is the structured protocol the course teaches (`seq`, namespaces, typed deltas), and its experimental status is contained: only `orchestration/streaming.py` knows v3, `langgraph` is pinned to the current minor (`>=1.2.24,<1.3`), and the beta warning is silenced only inside that module.
- D2: **A** (SSE reads Event v1 from the bus through a per-request `QueueSink`). One boundary between LangGraph's contract and ours; reuse what exists (recorder, redaction, bus) instead of rebuilding it; UI, JSONL and evals see the same data.
- D3: **A** (only the wrapper's `tool_started`/`tool_finished`; the adapter ignores v3 `tools` events). The wrapper sits inside the harness boundary: it knows the authorization decision, maps errors to the taxonomy and redacts through the recorder; LangGraph's events are raw duplicates.
- D4: **A** (`token` events are not written to JSONL: `JsonlSink(exclude_kinds={TOKEN})`). The log records what happened, not what was said, consistent with `run_started` carrying no user message; no full transcripts (PII) on disk, and the log stays small.
- D5: **A** (server creates `thread_id` via `POST /api/threads`, bound to `(tenant_id, user_id)`; every chat call runs `require_owner` first; unknown and foreign threads both → `404`). With a checkpointer, a thread id is the key to a conversation's history: a client-chosen id would let anyone who learns it read that conversation, across users and tenants; `404` for both cases reveals nothing.
- D6: **A** (client disconnect → cancel the run task; `stream_turn`'s `finally` records `run_finished(cancelled)` and re-raises `CancelledError`). No model calls for an answer nobody reads, and cancellations stay out of failure metrics (M07, M16). Schema: `RunStatus` gains `"cancelled"` within v1, with a new rule next to the versioning rule: consumers treat unknown statuses as "other"; snapshots regenerated.
- D7: **A** (explicit allowlist per kind and payload field in `api/sse.py`, default deny; table as in §7 unchanged; envelope fields `schema_version`, `seq`, `ts`, `request_id`, `namespace`, `kind` only). Everything sent is public to that user (DevTools); redaction protects every sink from known secrets, the allowlist decides what leaves the server, so a field or kind added later stays invisible to the browser until someone adds it on purpose.

### Explain-back
Scenario 2: An asks "Status of T-0002?", then "Who is it assigned to?" on the same thread; Binh then tries An's thread.

1. Before turn 1 the server creates the thread (`POST /api/threads`): a random `thread_id`, bound to An's `(tenant_id, user_id)` in the `ThreadRegistry`. The client never invents it (D5).
2. Turn 1 runs with `configurable.thread_id`. After every superstep the checkpointer (`InMemorySaver`) saves a checkpoint of the graph state under that `thread_id`. At the end the state's `messages` hold: the `HumanMessage`, the `AIMessage` with the `get_ticket` tool call, the `ToolMessage` with the `TicketView` (including `assignee_id = E-005`), and the final `AIMessage`.
3. Turn 2 sends the same `thread_id` and only the new question. `require_owner` confirms that An owns the thread. `stream_turn` invokes the agent with just the new `HumanMessage`; LangGraph loads the thread's latest checkpoint and the `add_messages` reducer appends the new message to the existing history.
4. The model receives the system prompt (added by the agent on every model call, not stored in the state), the whole history and the new question. The assignee is already in turn 1's `ToolMessage`, so the model answers without calling a tool. The model itself is stateless: it "remembers" only because the history is sent again as input. Identity (`ToolContext`) travels as `context`, outside the messages, so it is neither shown to the model nor checkpointed.
5. Binh: An's history is still in the checkpointer; it is not empty. Binh never reaches it. The `prepare_turn` dependency runs `require_owner` with Binh's `Principal` (built from his token, never from the body), the owner does not match, `ThreadNotFound` → `404`. This happens before the stream opens, before any run starts and before the checkpointer is read.
6. An unknown thread and someone else's thread get the same `404 "thread not found"`, so Binh cannot even learn that the thread exists. Without `require_owner` (break-it B1), the checkpointer would load An's history into Binh's run: the thread id alone would be the key.
