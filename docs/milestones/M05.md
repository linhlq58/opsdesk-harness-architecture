# M05 — Router pattern

**Goal:** a new **Router** tab in the UI. A router model reads the question, picks one or more specialists (ticket, knowledge, hardware, security, general), they run in parallel, and either the single specialist answers directly or a synthesizer merges their answers. The flow diagram lights up the nodes as they run, and the timeline shows which specialist called which tool. Knowledge and hardware specialists use **temporary in-process tools** that M08 (MCP) and M10 (RAG) will replace without touching any agent.

**Estimated effort:** 2 sessions. Session 1: decisions, tool registry and stub tools, specialist specs, router classification. Session 2: router graph, streaming/UI changes, demo, verification.

**How you learn in this milestone:** Claude Code writes all code. You (1) answer the Design decisions in §3, (2) predict the demo output, (3) run it and use the Router tab, (4) do the Break-it exercises, (5) go through the Review checklist, (6) explain one scenario back.

**Learning objectives:**
- The router pattern: a **structured-output** classification step decides *who* works; specialists do the work; a synthesis step merges (W1 L3).
- Model output is a **proposal** even when it is structured: the router's choice is validated against an allowlist and has a deterministic fallback (W1 L3, W3 L1).
- Per-specialist **least privilege**: each specialist gets only the tools it needs, through one registry (W1 L2–L3).
- Conversation state vs per-turn state in a LangGraph graph with a checkpointer (W2 L3 preview).
- Cost/latency of topologies: one route answers directly; several routes cost one extra synthesis call (W1 L5).

**Course topics:** W1 L3 (router, parallel execution, synthesis, fallback), W1 L2 (tool scoping), W1 L5 (call count vs latency vs cost), W2 L3 (state, `Send`, namespaces: preview).

## 3. Design decisions (🎯 you, before any code)

Record your choice and one sentence of reasoning under *Notes → Decisions*.

| # | Question | Options and consequences | Recommended |
|---|---|---|---|
| D1 | What runs the router flow? | **A** A LangGraph `StateGraph` (classify → `Send` to specialists → synthesize) with the checkpointer → multi-turn memory, parallel branches and v3 namespaces come for free; introduces `Send` a little before M12b. · **B** A plain-Python workflow with `asyncio.gather` → smallest abstraction, but you rebuild conversation memory and branch streaming yourself | **A** |
| D2 | What does a specialist receive? | **A** Only a **self-contained sub-query** written by the router (the router sees the conversation and resolves "it", "the other one") → least context, fewer tokens, no cross-domain leakage. · **B** The whole conversation → more context, more cost, every specialist sees everything | **A** |
| D3 | The router's output is invalid (no tool call, unknown agent name, empty list, more than 3 routes, duplicates). | **A** Deterministic sanitising: drop unknown agents and duplicates, cap at 3; if nothing valid is left → route to `general`; record `route_decided(fallback=true, reason=...)` → no extra cost, always an answer. · **B** Retry the router once, then fall back → sometimes better routes, one more call (retry policy is M15's topic). · **C** Fail the turn → honest but bad experience | **A** |
| D4 | Only one route was chosen. | **A** That specialist's answer is the final answer; no synthesis call → one model call fewer, lower latency. · **B** Always synthesize → uniform flow, extra cost and latency for every simple question | **A** |
| D5 | Which tokens stream to the chat? | **A** Only the **final** answer's tokens (single specialist, or the synthesizer); specialists of a multi-route turn appear in the flow diagram and timeline, not as text → readable chat. · **B** Stream every specialist, labelled → shows parallelism, but interleaved text is hard to read | **A** |
| D6 | Where do `node_started` / `node_finished` come from? | **A** Our graph nodes emit them through the recorder (explicit, our contract, same as the M04 decision for tools). · **B** The adapter derives them from LangGraph's v3 stream → less code in nodes, but our UI then depends on LangGraph's internal node names and lifecycle events | **A** |
| D7 | A specialist crashes (bug or model error) in a multi-route turn. | **A** The whole turn fails (`run_finished(failed)`), consistent with M03 D1. · **B** Synthesize what succeeded and label the missing part → better experience, but that is the partial-results lesson of M18a | **A** now |
| D8 | Employees cannot read assets (`asset:read` is IT-only, M02). How does the hardware specialist answer "is my laptop under warranty?" | **A** New scope `asset:read_own` for every employee; `list_my_devices` returns only devices assigned to the principal → a security-model change made in code with tests (the M02 rule). · **B** Reuse `ticket:read` → works, but the scope no longer means what it says. · **C** Only IT can ask about devices → simple, useless for employees | **A** |

## 5. Tools

### 5.1 `ToolRegistry` (🎯 decide & verify)

```python
class ToolRegistry:
    def register(self, tool: BaseTool, *, source: str = "internal") -> None: ...   # raises on duplicate name
    def select(self, names: Iterable[str]) -> list[BaseTool]: ...                   # raises on unknown name
    def names(self) -> frozenset[str]: ...
```

- One registry per app, built at startup. Specialists never import tools directly; they ask the registry for names listed in their spec.
- Duplicate name at registration → startup error (M08 adds namespacing for MCP tools; the collision check starts now).
- Unknown name in a spec → startup error, not a runtime surprise.

### 5.2 Temporary tools (📖)

| Tool | Scope | Behaviour | Replaced in |
|---|---|---|---|
| `search_faq(query, limit=3)` | `kb:read` | Case-insensitive keyword match over `faq.yaml`; returns entries with `id`, `title`, `answer`; `empty` when nothing matches | M10 (retrieval) |
| `list_my_devices()` | `asset:read_own` | Devices assigned to the principal in the principal's tenant; `empty` when none | M08 (MCP) |

Both go through `harness_tool`, return `ToolResult`, and emit tool events (roadmap rule 3: temporary adapters, permanent contracts).

## 6. Specialists as data (🎯 decide & verify)

```python
@dataclass(frozen=True, slots=True)
class AgentSpec:
    name: str                 # "ticket", "knowledge", ...
    description: str          # one line the router reads to choose
    prompt_file: str
    tool_names: tuple[str, ...]
    role: ModelRole = ModelRole.SPECIALIST
```

| Spec | Description for the router | Tools |
|---|---|---|
| `ticket` | Status and list of the user's own IT tickets | `get_ticket`, `list_my_tickets` |
| `knowledge` | How-to questions and IT policies (VPN, passwords, Wi-Fi, printers, laptop policy) | `search_faq` |
| `hardware` | The user's own devices: models, asset tags, warranty | `list_my_devices` |
| `security` | Suspected phishing, malware, lost devices, account compromise: first steps | `search_faq` |
| `general` | Greetings, unclear or out-of-scope questions; asks for clarification | none |

Rules:
- The router prompt is **generated from the specs** (name + description). Adding a specialist = adding a spec.
- A specialist's tools are exactly `tool_names`: least privilege per agent. The ticket specialist cannot see devices; the hardware specialist cannot see tickets.
- The **allowlist of valid routes** is the set of spec names; the router can never invent an agent.

## 7. Router graph (🎯 decide & verify)

### 7.1 State contract

```python
class RouterState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]       # conversation: kept across turns
    routes: list[Route]                                       # this turn only
    results: Annotated[list[SpecialistResult], operator.add]  # this turn only (parallel branches append)
    answer: str                                               # this turn only
```

- **Conversation fields** survive turns through the checkpointer; **per-turn fields** must be reset at the start of every turn. `results` uses an append reducer so parallel branches do not overwrite each other, which is exactly why it must be cleared explicitly each turn (see break-it B1).
- The final answer is appended to `messages` as an `AIMessage`, so the next turn's router sees it.

### 7.2 Nodes and edges

```
START → start_turn (reset per-turn fields)
      → classify (router model, sanitize, emit route_decided)
      → Send("specialist", {route}) × N         # parallel
      → specialist (child namespace, ToolContext per branch, run the spec's agent on route.query)
      → finalize: 1 result → answer = that result
                  N results → synthesize (synthesizer model) → answer
      → END
```

- Every node emits `node_started` / `node_finished` with `node` = `"classify"`, `"specialist:<name>"`, `"synthesize"` (D6).
- The specialist branch builds a **child** `ToolContext` whose recorder is `recorder.child("router", spec.name)`, so tool events carry the branch's namespace.

### 7.3 Classification and sanitising

```python
class Route(BaseModel):
    agent: str
    query: str          # self-contained (D2)

class RouteDecision(BaseModel):
    routes: list[Route]

def sanitize_routes(decision: RouteDecision | None, allowed: frozenset[str], *, max_routes: int = 3) -> SanitizedRoutes: ...
```

| # | Case | Expected |
|---|---|---|
| C1 | `[ticket, knowledge]` | Both kept, order preserved |
| C2 | `None` (no tool call) | `[general]`, `fallback=true`, `reason="no_decision"` |
| C3 | `[billing]` (unknown) | `[general]`, `fallback=true`, `reason="unknown_agent"` |
| C4 | `[ticket, billing]` | `[ticket]`, `fallback=false`, dropped agent recorded |
| C5 | `[ticket, ticket]` | `[ticket]` (deduplicated) |
| C6 | Five valid routes | First three kept, `reason="capped"` |
| C7 | Empty `query` in a route | That route dropped |

`route_decided` payload: `agents`, `fallback`, `reason`, `dropped` (names only; queries are **not** in the event).

## 8. Synthesis

- Synthesizer model role `SYNTHESIZER`; prompt: merge the specialist answers into one reply, keep each part's facts and codes, never add facts that are not in the answers, reply in the user's language.
- Input: the original question + the list of `(specialist, answer)`; not the specialists' tool results.

## 9. Streaming and events (🎯 decide & verify)

- `stream_turn` works for both the M03/M04 ticket agent and the router graph.
- Token filter (D5): forward `text-delta` only from the node that produces the final answer: the single specialist branch when there is one route, otherwise `synthesize`. The filter uses namespaces/`langgraph_node` from the v3 event, **in the adapter only**.
- Allowlist additions:

| Kind | Payload fields sent |
|---|---|
| `route_decided` | `agents`, `fallback`, `reason` |
| `node_started` | `node` |
| `node_finished` | `node`, `duration_ms` |

## 10. Threads per pattern and UI (📖 / ⚙️)

- `ThreadRegistry` stores the pattern a thread was created for; using a thread with another pattern → `404` (same as foreign/unknown).
- `POST /api/threads {pattern: "ticket_agent" | "router"}`.
- UI: tabs **Ticket agent** and **Router**, each with its own thread and Reset. Router tab shows a flow diagram (Query → Router → General / Ticket / Knowledge / Hardware / Security → Synthesize → Answer); nodes are *idle*, *working* (between `node_started` and `node_finished`) or *used this turn*; a "Routed to: ..." chip from `route_decided`; a fallback badge when `fallback` is true. Starter questions per tab.
