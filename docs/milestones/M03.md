# M03 — First agent across all 5 layers

**Goal:** an employee asks about their tickets in natural language and a real model answers, using tools that go through every harness layer: identity from the server, scope check, domain policy, typed result, recorded events. The same flow runs deterministically with a scripted fake model in tests and CI.

**Estimated effort:** 2 sessions. Session 1: design decisions, then Claude Code implements model factory, tool context and tool wrapper; you predict and run. Session 2: ticket tools, agent, turn runner, demo; break-it, review, explain-back.

**How you learn in this milestone:** Claude Code writes all code. You (1) answer the Design decisions in §3, (2) predict the demo output, (3) run it, (4) do the Break-it exercises, (5) go through the Review checklist, (6) explain one scenario back in your own words.

**Learning objectives:**
- How `create_agent` runs the model ↔ tool loop, and where the harness inserts itself in that loop (W1 L3).
- How trusted identity reaches a tool through **runtime context**, invisible to the model (W1 L2).
- Why a tool is a **boundary**: the model proposes arguments; the wrapper checks, decides and records (W1 L2, W3 L1).
- What the model should see from a tool (context engineering): a typed, safe result, not raw data or exceptions (W1 L2).

**Course topics:** W1 L2 (harness layers, trusted context, verification), W1 L3 (`create_agent`, tool calling), W1 L4 (local event contract).

## 2. Wiring: one tool call, end to end

An (E-001) asks: *"What's the status of T-0002?"*

| # | Step | Piece used | Built in |
|---|---|---|---|
| 1 | Load the employee, derive identity | `EmployeeRepository`, `principal_for` | M01, M02 |
| 2 | Build the per-request context | `RequestContext`, `new_request_id`, `new_thread_id`, `Workload.CHAT` | M02 |
| 3 | Start recording | `RunRecorder` → `EventBus` → `MemorySink` / `JsonlSink` | M02 |
| 4 | Emit `run_started` | `run_turn` | **M03** |
| 5 | Model reads the question, proposes `get_ticket(ticket_id="T-0002")` | `build_chat_model`, `create_agent` | **M03** |
| 6 | Tool receives identity + dependencies, invisible to the model | `ToolRuntime[ToolContext]` | **M03** |
| 7 | Emit `tool_started` (args redacted) | `harness_tool` wrapper + `RunRecorder` | **M03** + M02 |
| 8 | Coarse check: may this user read tickets at all? | `require_scope(principal, Scope.TICKET_READ)` | M02 |
| 9 | Validate the model's argument | `TicketId` format check | **M03** |
| 10 | Load the ticket, scoped by tenant | `TicketRepository.get(tenant_id, ticket_id)` | M01 |
| 11 | Fine check: may this user see **this** ticket? | `can_view_ticket` → `Decision` | M01 |
| 12 | Package the answer | `ToolResult.ok(TicketView)` / `result_from_decision` / `result_from_domain_error` | M02 + **M03** |
| 13 | Emit `tool_finished` (status, error code, duration) | wrapper + `RunRecorder` | **M03** + M02 |
| 14 | Model turns the result into an answer | `create_agent` loop | **M03** |
| 15 | Emit `run_finished` | `run_turn` | **M03** |

Everything below row 4 that says M01/M02 already exists. M03 is the glue, and the glue is the harness.

## 3. Design decisions (🎯 you, before any code)

Record your choice and one sentence of reasoning under *Notes → Decisions*. Claude Code implements a piece only after its decisions are recorded.

| # | Question | Options and consequences | Recommended |
|---|---|---|---|
| D1 | A business tool function hits a **bug** (e.g. `KeyError`). What does the wrapper do? | **A** Re-raise immediately; the event log shows `tool_started` with no `tool_finished`, and `run_turn` records `run_finished(failed)` → simple, honest, the gap itself is the signal. · **B** Add a new event kind `tool_crashed` (allowed in v1: additive), emit it, then re-raise → clearer timeline, one more kind to maintain. · **C** Emit `tool_finished(unavailable)` and re-raise → misleading: a bug is reported as an infrastructure outage | A now; B can come with resilience in M15 |
| D2 | What does the **model** receive from a tool? | **A** The whole `ToolResult` as JSON (`status`, `data`, `safe_message`, `error_code`) → the model sees exactly what UI/eval see; codes are designed to be safe. · **B** Hide `error_code` → slightly less for the model to misuse, but its explanation gets vaguer. · **C** A plain sentence → easy to read, but the model loses structure and evals cannot check it | A |
| D3 | Minh (Globex) asks for an Acme ticket. What is the result? | **A** `not_found`: the tenant-scoped repository simply does not find it → no information leaks. · **B** `denied / cross_tenant` → clearer when debugging, but confirms to another company that the ticket exists | A |
| D4 | How is a **malformed ticket id** (`"abc"`) rejected? | **A** In the tool's args schema (regex pattern) → LangChain rejects it *before* the wrapper runs: no `tool_started`/`tool_finished` events and no `ToolResult` envelope, the model gets a framework error string. · **B** Accept any string, validate inside the tool → `ToolResult.invalid` with events, like every other failure | B: every failure goes through the same envelope and event log |
| D5 | Which fields does `TicketView` expose to the model? | **A** Minimal: id, title, status, priority, category, assignee_id, created_at, updated_at. · **B** A + description → better answers, but more tokens and free text written by people (a future injection channel, M13). · **C** A + assignee **name** → friendlier answers, one extra repository call per ticket | A now (context engineering: start small, add with a reason) |
| D6 | Does `list_my_tickets` bound its output? | **A** No limit → fine for seed data, unbounded tokens in production. · **B** `limit` argument, default 10, max 20, results oldest first → bounded context; the model can ask for more | B |

### 5.2 `build_chat_model` (🎯 decide & verify)

```python
class ModelRole(StrEnum):
    ROUTER = "router"
    SPECIALIST = "specialist"
    SYNTHESIZER = "synthesizer"
    JUDGE = "judge"

def build_chat_model(role: ModelRole, settings: LlmSettings) -> BaseChatModel: ...
```

Rules:
- One function decides which model serves which **role**. Agents never name a model; they ask for a role. (M21's cheaper-router experiment is then one line in `.env`.)
- Missing API key or missing model name for the role → a clear startup error naming the env variable, not a 401 from the gateway on the first question.
- Settings come in as a parameter: the factory does not read the environment itself (testable).
- Callbacks (tracing, usage) will be attached here in M07; leave a single place where that will happen.

### 5.3 `ScriptedChatModel` (📖)

A `GenericFakeChatModel` subclass whose `bind_tools` returns `self`, fed with a list of `AIMessage`s (some carrying `tool_calls`). Tests and the demo inject it in place of a real model; the agent cannot tell the difference. This is why agents take the model as a **parameter** instead of calling the factory themselves.

## 6. Tool context (🎯 decide & verify)

```python
@dataclass(frozen=True, slots=True)
class ToolContext:
    request: RequestContext   # who, which turn, which thread
    repos: Repositories       # data access (in-memory in tests, SQLite in the CLI)
    recorder: RunRecorder     # events for this turn
    clock: Clock
```

- Passed as `context=` to `agent.ainvoke(...)` and declared as the agent's `context_schema`.
- Reaches each tool as `runtime: ToolRuntime[ToolContext]`. The model never sees it, so it can neither read nor forge identity.
- This is dependency injection: tools receive what they need; they do not import global state.

## 7. Tool wrapper (🎯 decide & verify)

The heart of this milestone: one function that turns a plain async business function into a LangChain tool **with the harness around it**.

```python
type ToolFn[A: BaseModel, T] = Callable[[ToolContext, A], Awaitable[ToolResult[T]]]

def harness_tool[A: BaseModel, T](
    *, name: str, description: str, args_schema: type[A], scope: Scope
) -> Callable[[ToolFn[A, T]], BaseTool]: ...
```

What the generated tool does, in this order:

1. Read `ToolContext` from `runtime.context`.
2. Emit `tool_started` with the (redacted) arguments.
3. `require_scope(principal, scope)`; if denied → `result_from_decision(...)`, skip the business function.
4. Call the business function with the validated arguments model.
5. If it raises a `DomainError` → `result_from_domain_error(...)`. **Any other exception propagates**: a bug must fail loudly, not be turned into a polite message.
6. Emit `tool_finished` with `status`, `error_code`, `duration_ms` (measured with `time.perf_counter`; it is a duration, not a business timestamp) and a short `summary`.
7. Return the `ToolResult` serialised as JSON to the model.

Cases to cover in tests:

| # | Case | Expected |
|---|---|---|
| W1 | Scope present, function returns `ok` | `tool_started`, `tool_finished(ok)`; model receives the JSON result |
| W2 | Scope missing | Function **not called**; `denied` / `missing_scope` |
| W3 | Function raises `NotPermitted(reason=...)` | `denied` with that reason code |
| W4 | Function raises `KeyError` | Exception propagates; `tool_finished` is **not** emitted as `ok` |
| W5 | Arguments contain a key named `password` | Redacted in the `tool_started` event |
| W6 | The model-visible tool schema | Contains only the business arguments, never `runtime` |

W4 follows decision **D1**; W6 and the "model receives" step follow **D2**.

The system prompt (keep it short, it is a file so it can be reviewed and diffed) must say:

## 10. Turn runner (🎯 decide & verify)

```python
@dataclass(frozen=True, slots=True)
class TurnResult:
    answer: str
    status: Literal["completed", "failed"]

async def run_turn(
    agent: CompiledStateGraph, *, ctx: RequestContext, message: str,
    repos: Repositories, bus: EventBus, clock: Clock, entrypoint: str,
) -> TurnResult: ...
```

- Creates the `RunRecorder` from `ctx.request_id` / `ctx.thread_id`, emits `run_started`.
- Invokes the agent with `context=ToolContext(...)`.
- Emits `run_finished` with `completed` or `failed` and `duration_ms` **in a `finally`**, so a crash still closes the run in the event log.
- Single turn: no conversation memory yet (M04).

Verified behaviour (probes run on these versions):
- `runtime: ToolRuntime[Ctx, ...]` in the tool coroutine's signature is removed from the model-visible schema; `runtime.context` is the object given as `ainvoke(..., context=...)`.
- **Default tool-error handling** of the agent's tool node (`_default_handle_tool_errors`): a `ToolInvocationError` (the model's arguments fail `args_schema` validation) is turned into an error `ToolMessage` for the model; **every other exception is re-raised** and aborts the run. So "bugs propagate" (D1-A) is the default; the wrapper must not undo it.
- Consequence for T6: a `pattern=` on the args schema rejects `"abc"` *before* the wrapper runs (no events, LangChain's own error text instead of a `ToolResult`). Hence D4-B: the format check lives in `domain.ids.parse_ticket_id`, raising `InvalidIdentifier` (a `DomainError`, mapped to `invalid` / `invalid_id` in `tools.taxonomy`).
- Putting a `ToolRuntime[ToolContext]` field into a Pydantic args schema fails at schema build time (`ToolContext` holds Protocol-typed repositories). Keep `runtime` out of `args_schema`.
- Pyright strict: `langgraph` is a namespace package, so pyright misses its `py.typed`; `create_agent` shows up as "partially unknown". Handled with one-line `# pyright: ignore[...]` at the call sites, not by relaxing strict mode.

### Decisions
- D1: **A**. A bug re-raises immediately: `tool_started` without `tool_finished`, then `run_finished(failed)`. Simple and honest; the gap is the signal. (`tool_crashed` may come with resilience in M15.)
- D2: **A**. The model receives the whole `ToolResult` JSON, the same envelope the UI and evals see.
- D3: **A**. Cross-tenant is `not_found` from the tenant-scoped repository; no existence leak.
- D4: **B**. Any string accepted; format checked inside the tool → `invalid` with events, like every other failure.
- D5: **A**. Minimal `TicketView`; add fields only with a reason.
- D6: **B**. `limit` default 10, max 20, oldest first. Out-of-range values are **clamped inside the tool** (above 20 → 20, below 1 → 1) rather than rejected by the schema, so they still go through the harness (same reasoning as D4-B).
- Temperature (added after the first live run, 2026-11-23): **B**. `OPSDESK_LLM_TEMPERATURE` is unset by default and an unset temperature is **not sent** to the model. Reason: the gateway's reasoning model (`gpt-6-luna`) rejects `temperature=0.0` with a 400; a harness should not send by default a parameter some models refuse. Trade-off: runs are no longer reproducible by default; set it explicitly where that matters (the M07 judge).
- Follow-up (implementer, same spirit as D1-A): `run_turn` re-raises after emitting `run_finished(failed)`; it never returns `TurnResult(status="failed")`. Entry points decide what the user sees (the CLI catches and logs).
